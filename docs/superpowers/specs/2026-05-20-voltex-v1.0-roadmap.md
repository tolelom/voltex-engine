# Voltex Engine v1.0 Roadmap

**작성일**: 2026-05-20
**범위**: 메타 로드맵 (각 사이클의 정식 spec 은 별도 문서)
**상태**: 작성 완료, 사용자 검토 대기 → 승인 후 cycle 1 부터 세션 단위 실행

이 문서는 v1.0 까지 남은 모든 작업을 **15개의 cycle 단위** + **총 37 세션** 으로 분해하고, 각 cycle 의 범위/완료기준/의존성/세션 분할을 정의한다. 매 세션 = "컨텍스트 0 → brainstorm/plan/impl → master 머지" 한 묶음. cycle 의 첫 세션이 해당 cycle 의 brainstorm + plan + impl 시작을 함께 처리한다.

---

## 1. v1.0 Definition of Done

외부 사용자가 다음 두 워크플로 중 **어느 쪽으로도** 엔진을 사용할 수 있을 때 v1.0 release.

### 1.1 Code-first 워크플로 (Bevy/Macroquad 스타일)

1. `git clone https://git.tolelom.xyz/tolelom/game_engine`
2. README 의 5분 가이드만 보고 `cargo run --example triangle` 성공
3. `use voltex::prelude::*;` 로 시작하는 자기 게임 코드 작성
4. `cargo build --release` 로 자기 OS 의 단일 실행 파일 산출

### 1.2 Editor 워크플로 (Unity/Godot 스타일)

1. 같은 clone + README
2. `cargo run -p voltex_cli --bin voltex_editor` 로 에디터 실행
3. 빈 씬에서 시작 → Spawn / gizmo 로 배치 → Lua 스크립트로 동작 → Save
4. **Play** 버튼으로 에디터 내 시뮬레이션 확인 → **Stop** 으로 씬 원상복구
5. **Build** 으로 `voltex.toml` 매니페스트 기반 단일 exe 산출 (Windows / macOS / Linux 셋 다)

### 1.3 Quality gates (1.1/1.2 외)

- 공개 API 100% rustdoc (`cargo doc --workspace --no-deps` 경고 0)
- 800+ 테스트 통과
- 30분 튜토리얼 텍스트 + 스크린샷
- Flagship game = survivor_game 을 editor workflow 로 재제작한 결과물 + 3 OS exe artifact

## 2. Sub-projects

코드/문서 기여를 6개의 sub-project 로 분류. 각 cycle 은 어느 sub-project 에 속하는지 라벨링됨.

| ID | 이름 | 범위 |
|----|-----|------|
| **C** | Core bridge | ECS ↔ Renderer 브릿지 (현재 부재) — 모든 후속 시각 검증의 전제 |
| **E** | Editor v1 | 선택/조작 (gizmo + AABB picking), Play/Stop 모드, command 확장 |
| **S** | Scripting v1 | per-entity Lua ScriptComponent, world query iterator from Lua |
| **B** | Build pipeline | `voltex_runtime` 라이브러리, `voltex` CLI, `voltex.toml` 매니페스트, asset packing, 멀티 OS exe |
| **P** | Platform abstraction | audio backend trait, Linux ALSA, macOS CoreAudio |
| **A** | API consolidation | facade prelude 완성, 공개 API rustdoc 전수, breaking change lock |
| **D** | Docs + flagship | README + getting-started + 30분 튜토리얼 + flagship game 재제작 |

## 3. Cycle 시퀀스

순서: critical path 우선 (Slice 1 = end-to-end 슬라이스, Slice 2 = 플랫폼 broaden, Slice 3 = 외부 사용자 onboarding). Cycle 12 (E3) 만 flex 위치 (의존성 없음, 6~11 사이 아무 때).

### Slice 1 — MVP end-to-end

#### Cycle 1: C0a — ECS rendering 컴포넌트  [✅ 1/1] (commit 1a56ac9)
- Spec: docs/superpowers/specs/2026-05-20-c0a-ecs-render-components-design.md
- Plan: docs/superpowers/plans/2026-05-20-c0a.md

- **Sub-project**: C
- **목표**: Transform 외에 렌더링에 필요한 데이터를 ECS 측에 정의. 아직 실제 렌더링 통합은 안 함 (C0b 의 일).
- **Scope**:
  - `voltex_ecs::MeshHandle(Handle<Mesh>)` 컴포넌트
  - `voltex_ecs::MaterialHandle(Handle<Material>)` 컴포넌트
  - `voltex_ecs::Bounds(Aabb)` 컴포넌트 (메시 AABB 캐시)
  - `Component` trait 구현 + `register_defaults()` 에 포함 여부 결정 (built-in 으로 넣을지 옵션으로 둘지)
  - 시리얼라이즈: Handle 는 generation+index 두 정수, Aabb 는 min/max 두 Vec3
- **Out-of-scope**: 실제 렌더링 호출, voltex_renderer 측 변경, editor_demo 변경
- **Done 기준**:
  - 컴포넌트 3개 신규 + Component impl + 직렬화 라운드트립 테스트
  - voltex_ecs lib 테스트 +6 이상
  - `cargo build --workspace` 깨끗
- **의존**: 없음
- **세션 수**: **1**
  - **세션 1**: 컴포넌트 3종 정의 + Component impl + register_defaults 통합 + 직렬화 라운드트립 테스트
- **주의**: `voltex_ecs` 는 L1 (math 만 의존). Handle<T> 는 voltex_asset 의 타입 — L1 → L0 (asset 은 L0) 이므로 OK. Aabb 는 voltex_math 에 이미 존재.

#### Cycle 2: C0b — Renderer 브릿지 + 첫 ECS-driven 렌더링  [✅ 2/2]
- Spec: docs/superpowers/specs/2026-05-20-c0b-renderer-ecs-bridge-design.md
- Plan: docs/superpowers/plans/2026-05-20-c0b.md

- **Sub-project**: C
- **목표**: 신규 crate `voltex_renderer_ecs` 로 ECS World 를 renderer 가 그릴 수 있도록 연결. editor_demo / survivor_game 를 이 경로로 마이그레이션.
- **Scope**:
  - 신규 crate `voltex_renderer_ecs` (L3): voltex_ecs + voltex_renderer + voltex_asset 의존
    - `render_world(world, &Assets<Mesh>, &Assets<Material>, encoder, ...) → ()` 함수
    - per-entity dynamic UBO 패턴 (many_cubes 의 코드 일반화)
    - WorldTransform → 모델 행렬 자동 변환
  - editor_demo 리팩토링: `scene_meshes: Vec<Mesh>` 제거, ECS 에 MeshHandle/Bounds 세팅 → 뷰포트가 World 를 iterate
  - survivor_game 리팩토링: 동일
  - 시각 검증: gizmo 가 아직 없어도 ECS dispatch 로 Transform 변경 → 뷰포트 반영
- **Out-of-scope**: gizmo, picking 업그레이드 (E1 의 일)
- **Done 기준**:
  - 두 example 의 평행 Vec 구조 완전 제거
  - `voltex_renderer_ecs` 단위 테스트 +4 이상 (모델 행렬 변환, 가시성, 비어있는 World 케이스)
  - editor_demo 에서 Inspector 슬라이더로 Transform.position 변경 → 뷰포트의 큐브가 따라 움직임 (수동 검증, 스크린샷 첨부 권장)
  - 빌드/테스트 깨끗
- **의존**: Cycle 1 (C0a 컴포넌트 필요)
- **세션 수**: **2**
  - **세션 1**: `voltex_renderer_ecs` crate 신설 + `render_world` 함수 + per-entity dynamic UBO 패턴 + 단위 테스트
  - **세션 2**: editor_demo + survivor_game 의 평행 Vec<Mesh> 구조를 ECS-driven 렌더링으로 마이그레이션, 시각 검증
- **주의**:
  - 현재 `voltex_renderer` 의 PBR 파이프라인은 group 0~3 의 4개 bind group 사용. ECS 측 dynamic offset 패턴이 group 3 의 per-entity uniform 과 부딪힐 수 있음 → many_cubes 코드 참조
  - voltex facade 의 `voltex::renderer_ecs` 모듈로 re-export 결정 (M6 패턴)

#### Cycle 3: E1 — Gizmo + AABB picking  [✅ 2/2]
- Spec: docs/superpowers/specs/2026-05-20-e1-gizmo-aabb-picking-design.md
- Plan: docs/superpowers/plans/2026-05-20-e1.md

- **Sub-project**: E
- **목표**: 선택한 엔티티를 시각적으로 조작. picking 정확도를 sphere 근사에서 AABB 로 업그레이드.
- **Scope**:
  - 3축 translate gizmo: 화살표 3개, 마우스 드래그 → 축 방향 평면에 ray cast → 델타로 `EditorCommand::SetTransform` dispatch
  - 3축 rotate gizmo: 링 3개, 드래그 → 각도 델타
  - 3축 scale gizmo: 박스 3개, 드래그 → 스케일 델타
  - AABB picking: `picking::pick_entity` 가 sphere 대신 Bounds 컴포넌트의 AABB 와 ray 교차 검사 → 가장 가까운 hit
  - gizmo 자체 렌더링은 별도 단순 wireframe (Forward 패스, depth test off)
- **Out-of-scope**: snap-to-grid, multi-select, OBB (회전된 박스) picking
- **Done 기준**:
  - 3종 gizmo 모두 정상 드래그 + `EditorCommand::SetTransform` 로 dispatch → undo/redo 동작
  - AABB picking 정확도 테스트 (회전된 박스 외곽, 겹친 박스 등 케이스 다수)
  - voltex_editor 테스트 +15 이상
  - editor_demo 에서 큐브 선택 → 드래그 → 위치/회전/크기 변경 → Save → Load → 일관성
- **의존**: C0b (시각 검증 가능 상태)
- **세션 수**: **2**
  - **세션 1**: AABB picking 업그레이드 (Bounds 컴포넌트 사용) + translate gizmo (3축 화살표 + 드래그 → SetTransform)
  - **세션 2**: rotate gizmo (3축 링) + scale gizmo (3축 박스)
- **주의**:
  - gizmo 의 hit detection 은 viewport ray 와 gizmo 의 화면 공간 박스 교차. picking helpers (`ndc_from_viewport`, `ray_from_ndc`) 재사용
  - rotate gizmo 의 ring vs ray 는 disk 평면 교차 → 반지름 검사

#### Cycle 4: E2 — Play/Stop 모드 + 시스템 라이프사이클 훅  [✅ 3/3]
- Spec: docs/superpowers/specs/2026-05-20-e2-play-stop-lifecycle-design.md
- Plan: docs/superpowers/plans/2026-05-20-e2.md

- **Sub-project**: E
- **목표**: 에디터에서 Play 누르면 World 시뮬레이션 실행, Stop 누르면 원상복구. 후속 cycle (S1, audio 등) 이 사용할 라이프사이클 훅 인프라 정의.
- **Scope**:
  - `EditorMode { Edit, Play }` enum + `EditorSession::set_mode(...)`
  - Play 진입 시: 현재 World 상태를 `serialize_scene_binary` 로 스냅샷 저장 → 메모리에 보관
  - Stop 진입 시: `World::clear()` + 스냅샷에서 deserialize → 원상복구
  - Play 중에는 `EditorCommand` dispatch 시 `EditorError::ModeMismatch` 반환 (정책). UI 측은 부가적으로 Toolbar 버튼들을 disable.
  - 시스템 라이프사이클 trait: `SystemLifecycle { fn on_play_start(&mut self, world: &mut World); fn on_play_stop(&mut self, world: &mut World); }` (또는 콜백 리스트)
  - Toolbar 에 Play/Stop 버튼 추가
  - Play 중 physics + audio 가 동작하는 데모 (rigid body 떨어짐)
- **Out-of-scope**: Pause, Step (1프레임), Play-mode-only 시스템 분리 (모든 시스템이 두 모드 다 도는 단순화)
- **Done 기준**:
  - Play → 큐브에 RigidBody 컴포넌트 + 중력 → 떨어짐 → Stop → 원위치
  - 스냅샷 라운드트립이 ComponentRegistry 의 모든 등록 컴포넌트 보존
  - voltex_editor 테스트 +10 이상
  - 라이프사이클 훅 인터페이스 (S1 가 다음 cycle 에서 채울 빈 슬롯) 문서화
- **의존**: C0b, C0a (Bounds/MeshHandle 도 스냅샷 대상)
- **세션 수**: **3**
  - **세션 1**: 설계 + `EditorMode` enum + World snapshot/restore 기본 동작 + 라운드트립 테스트
  - **세션 2**: `EditorError::ModeMismatch` dispatch 정책 + `SystemLifecycle` trait 정의 + 라이프사이클 콜백 인프라
  - **세션 3**: Toolbar Play/Stop 버튼 + physics 데모 (rigid body 떨어짐) + 카메라 조작 정책 + 미등록 컴포넌트 경고
- **주의**:
  - 모든 stateful 컴포넌트가 ComponentRegistry 에 등록되어 있어야 Play→Stop 이 손실 없음. 미등록 컴포넌트는 silent loss → 명시적 경고 로그 필요
  - "Play 중에도 카메라는 조작 가능" 정의 필요 (orbit/free 모두)

#### Cycle 5: S1 — per-entity Lua ScriptComponent + world query iterator  [✅ 2/2]
- Spec: docs/superpowers/specs/2026-05-21-s1-script-component-design.md
- Plan: docs/superpowers/plans/2026-05-21-s1.md

- **Sub-project**: S
- **목표**: 한 엔티티에 Lua 스크립트를 붙여 on_start/on_update 콜백이 돌도록. Lua 측에서 World 를 순회할 수 있도록 iterator 노출.
- **Scope**:
  - `voltex_ecs` 측: `ScriptComponent { script_path: String, instance_id: u32 }` (+ Component impl)
  - `voltex_script` 측: `ScriptInstance` 풀 + 각 인스턴스의 LuaState 격리
  - 시스템: `script_update_system(world, lua_engine, dt)` — 각 ScriptComponent 의 on_update(entity_id, entity_gen, dt) 호출
  - Lua API 확장 (현재 15개 → 17개): `world.iter_entities() → Lua iterator`, `world.iter_by_tag(tag) → Lua iterator`
  - Cycle 4 의 라이프사이클 훅 채우기: Play 시작 시 모든 ScriptComponent 의 on_start, Stop 시 on_destroy (옵션)
  - 핫리로드: 스크립트 파일 변경 → reload_file + 영향받는 인스턴스만 재초기화 (FileWatcher 이미 있음)
- **Out-of-scope**: Lua → Rust 사용자 컴포넌트 정의 (raw byte 만 사용), debugger, profiler
- **Done 기준**:
  - 한 큐브에 spinner.lua (계속 회전) 붙여서 Play → 회전, Stop → 멈춤
  - iterator 로 5개 큐브를 동시에 회전시키는 데모
  - voltex_script 테스트 +8 이상
- **의존**: E2 (라이프사이클 훅), C0a (ScriptComponent 가 Component trait)
- **세션 수**: **2**
  - **세션 1**: `ScriptComponent` + `ScriptInstance` 풀 + `script_update_system` + on_start/on_update 콜백 + spinner.lua 데모
  - **세션 2**: Lua iterator API 2종 (`iter_entities`, `iter_by_tag`) + FileWatcher 기반 핫리로드 통합 + 영향받은 인스턴스 재초기화

#### Cycle 6: B0 — voltex_runtime 라이브러리 crate  [✅ 3/3]
- Spec: docs/superpowers/specs/2026-05-21-b0-voltex-runtime-design.md
- Plan: docs/superpowers/plans/2026-05-21-b0.md

- **Sub-project**: B
- **목표**: 표준화된 게임 부트스트랩 + 메인 루프. 단일 라이브러리. CLI 는 다음 cycle.
- **Scope**:
  - 신규 crate `voltex_runtime` (L3): voltex 모든 sub-crate 의존 (facade 와 같은 레벨)
  - `RuntimeApp` 구조체: window, GpuContext, World, ComponentRegistry, Scheduler, AssetLoader, AudioSystem, LuaEngine, InputState, GameTimer 다 보유
  - `RuntimeApp::run(config: RuntimeConfig) -> RuntimeResult<()>` — 부트스트랩 + 메인 루프
  - `RuntimeConfig`: window title/size, 초기 scene path, 초기 컴포넌트 registry 채우는 콜백, 사용자 시스템 등록 콜백

- **Done 기준**:
  - `examples/runtime_demo` 가 hierarchy_demo 와 시각적으로 동일
  - 사용자 main.rs 가 `voltex_runtime::RuntimeApp::default().with_scene("scene.vscn").run()` 같은 한 줄로 동작
  - voltex_runtime 단위 테스트 +5 이상 (config 빌드, 시스템 등록, 셧다운 정합성)
- **의존**: C0b (ECS rendering), S1 (script system 통합)
- **세션 수**: **3**
  - **세션 1**: 설계 (RuntimeApp phase 별 시퀀스 다이어그램) + `RuntimeConfig` builder + crate 골격
  - **세션 2**: `RuntimeApp` main loop + 기본 시스템 등록 (world_transform/physics_step/audio_sync/script_update/render_world)
  - **세션 3**: `examples/runtime_demo` + 셧다운 정합성 + 에러 경로 + 단위 테스트
- **주의**:
  - max_bind_groups=4 제약 유지
  - facade 와의 관계: voltex 는 "라이브러리 컬렉션", voltex_runtime 은 "조립된 앱". 둘 다 L3/L4 에 공존.

#### Cycle 7: B1-spike — 작동하는 prototype CLI (1세션 timebox)  [✅ 1/1]
- Spec: docs/superpowers/specs/2026-05-21-b1-spike-design.md
- Learnings: docs/superpowers/notes/2026-05-21-b1-spike-learnings.md

- **Sub-project**: B
- **목표**: B1 의 미지수 (CLI 구조, project 폴더 레이아웃, exe 산출 메커니즘) 를 prototype 으로 한 번 통과시켜본다. **timebox**: 1 세션. 산출은 dirty 해도 OK, 단 학습이 남아야 함.
- **Scope**:
  - 신규 bin crate `voltex_cli` (facade crate `voltex` 와 이름 충돌 회피) — `crates/voltex_cli/` 에 위치, bin 이름은 `voltex` (사용자는 `voltex build` 로 호출)

#### Cycle 9: B2 — Asset packing + VFS  [✅ 2/2]
- Spec: docs/superpowers/specs/2026-05-21-b2-asset-packing-vfs-design.md

- **Sub-project**: B

   - `git pull --ff-only` (autonomous 루프가 master 에 push 했을 수 있음 — MEMORY.md 의 `project_autonomous_loop` 참조)
   - `cargo build --workspace` / `cargo test --workspace --lib` 둘 다 깨끗한지 확인
   - 이 로드맵 (`2026-05-20-voltex-v1.0-roadmap.md`) 열어서 cycle 번호 + 의존 cycle 모두 완료 상태 확인

2. **Brainstorm** (cycle 1 = N 의 spec 작성)
   - `superpowers:brainstorming` 스킬 invoke
   - 로드맵의 cycle N 블록을 출발점으로 → 사용자와 디테일 확정 → `docs/superpowers/specs/YYYY-MM-DD-<cycle-code>-design.md` 작성
   - cycle 가 너무 크면 추가 분할 가능 (해당 cycle 의 entry 를 N-a / N-b 로 in-place 갱신)

3. **Plan**
   - `superpowers:writing-plans` 스킬 invoke
   - `docs/superpowers/plans/YYYY-MM-DD-<cycle-code>.md` 작성

4. **Implement**
   - `superpowers:executing-plans` (또는 직접 plan 따라가기)
   - 단일 책임 원칙, 600줄 한도, 일관된 패턴 (CLAUDE.md 변경 워크플로 따름)
   - 매 단계 commit (단일 책임 단위)

5. **Verify**
   - `superpowers:verification-before-completion` 으로 cycle 의 done 기준 모두 충족 확인
   - `cargo build --workspace` + `cargo test --workspace --lib` 깨끗
   - UI 변경이라면 실제 실행 + 스크린샷
   - 영향받은 CODEMAP.md / STATUS.md 갱신

6. **종료**
   - 로드맵 cycle 블록의 상태를 ✅ 로 갱신
   - `STATUS.md` 의 "다음 작업 후보" 갱신
   - master 머지 (autonomous 루프 끄거나 pre-commit 정리 후 push)

## 5. 세션 간 핸드오프 프로토콜

다음 세션이 컨텍스트 0 상태에서 이 로드맵을 어떻게 픽업하는지.

### 5.1 한 cycle 의 진행 상태 추적

각 cycle 의 헤더 옆에 진행 마커를 단다:

- `[ ]` pending
- `[~]` in progress (현재 세션이 작업 중 — 다른 세션이 함부로 같은 cycle 진입하지 않도록)
- `[✅]` done — done commit hash 와 spec/plan 경로 추가

예시:

```
#### Cycle 1: C0a — ECS rendering 컴포넌트  [✅ 1/1] (commit abc1234)
- Spec: docs/superpowers/specs/2026-05-21-c0a-ecs-render-components-design.md
- Plan: docs/superpowers/plans/2026-05-22-c0a.md

#### Cycle 4: E2 — Play/Stop 모드 + 시스템 라이프사이클 훅  [~ 2/3]
- 세션 1 ✅ (commit def5678): Mode enum + snapshot/restore
- 세션 2 ✅ (commit ghi9012): dispatch 정책 + lifecycle hook trait
- 세션 3 in progress
```

### 5.2 새 세션 진입 절차

1. `git pull --ff-only`
2. 이 로드맵 파일 열기
3. 마커 표 보고 첫 `[ ]` cycle 선택 (또는 명시적으로 flex cycle 12 를 끼워넣을지 결정)
4. 해당 cycle 블록을 `[~]` 로 마크 + 작업 중인 세션 정보 commit (옵션)
5. 4번 항목의 표준 흐름 실행

### 5.3 컨텍스트 보존

- 이 로드맵은 단독으로 읽혀야 함 (다른 세션의 conversation 없이도 cycle 진입 가능)
- 각 cycle 의 spec/plan 도 단독으로 읽혀야 함 (spec → impl, plan → impl 둘 다)
- STATUS.md 는 사후 요약 (역사 기록), 로드맵은 사전 계획. 둘 다 갱신.
