# DependencyScheduler 병렬 실행 — YAGNI 판정

- 날짜: 2026-10-12
- 출처: `docs/AUDIT-BACKLOG.md` B1 (보류 항목), CLAUDE.md 용어집 "실제 병렬 실행은 future work"
- 결론: **구현하지 않는다.** 그룹 빌드(`build_schedule`)만 있는 지금 상태를 유지한다.

## 확인한 사실

1. **`World`는 `Send`도 `Sync`도 아니다** (2026-10-12 컴파일 확인). 컴포넌트 저장소가 `Box<dyn ComponentStorage>`(`trait ComponentStorage: Any`, 스레드 바운드 없음)이고 리소스가 `Box<dyn Any>`이다. `std::thread::scope`로 시스템 둘에 `World`를 나눠 주는 것은 unsafe 없이는 컴파일되지 않는다.
2. **시스템 시그니처가 `FnMut(&mut World)`다.** 시스템마다 World 전체에 대한 배타 대여를 받는다. `SystemAccess`의 read/write 선언은 타입 시스템이 강제하지 않는 *자기 신고*다. 신고와 다르게 접근하는 시스템이 하나라도 있으면 병렬 실행은 데이터 경쟁(UB)이 된다.
3. 접근 집합이 겹치지 않아도 `World::add`가 저장소를 **지연 생성**한다(`storages.entry(...).or_insert_with`). 그래서 서로 다른 컴포넌트를 쓰는 두 시스템도 같은 `HashMap`을 동시에 구조 변경할 수 있다.
4. 소비자가 0이다. 저장소 안의 게임·예제 중 `DependencyScheduler`를 쓰는 곳이 없다. 어느 게임에서도 시스템 실행이 프레임 시간을 지배한다는 측정이 없다.

## 병렬 실행에 실제로 필요한 것

- 저장소·리소스에 `Send + Sync` 바운드를 추가한다(전 컴포넌트 타입에 전파되는 breaking change).
- 시스템 시그니처를 "선언한 것만 대여받는" 파라미터 방식(`Query<&T>`, `ResMut<R>` 등)으로 바꾼다. 그래야 신고와 실제 접근이 타입으로 일치한다. 이건 ECS API 전면 재설계다.
- 저장소를 실행 전에 미리 만들어 두는 단계를 둔다(지연 생성 경쟁 제거).

셋 다 소비자가 없는 기능을 위해 모든 게임 코드를 바꾸는 일이다. 근거가 될 측정(시스템 실행이 프레임 병목이라는 것)도 없다.

## 다시 볼 조건

다음 중 하나가 생기면 이 판정을 재검토한다.

- 프로파일로 시스템 실행이 프레임 시간의 의미 있는 비율(예: 30% 이상)을 차지하는 게임이 나온다.
- ECS API를 다른 이유로 파라미터 방식 시스템으로 재설계하게 된다. 그때 병렬성은 거의 공짜로 따라온다.

그 전까지 `DependencyScheduler`는 "충돌 분석 + 그룹 빌드" 도구로 남긴다(문서·테스트 있음, 유지 비용 낮음).
